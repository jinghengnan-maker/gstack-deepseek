## See it work（它怎么干活）

一次典型的冲刺长这样：

```
你：      我想做一个每日简报 App，读我的日历。
你：      /office-hours
DeepSeek：[问痛点——问的是具体例子，不是假设性问题]

你：      我有好几个 Google 日历，事件信息经常是过期的，地点还写错。
          准备一次要花很久，而且出来的东西还不能用……

DeepSeek：我要顶一下你的框架。你说的是「每日简报 App」，
          但你真正描述的是一个**个人幕僚长 AI**。
          [把你没意识到自己在描述的 5 个能力抽出来]
          [挑战 4 个前提——你同意、不同意，或者调整]
          [给出 3 条实现路线，附工作量估计]
          建议：明天先做最窄的那一刀，从真实使用里学。
          完整愿景是三个月的项目——先做那个真的能用的每日简报。
          [写出设计文档 → 自动喂给下游技能]

你：      /plan-ceo-review
          [读设计文档，挑战范围，跑 10 个环节的评审]

你：      /plan-eng-review
          [画 ASCII 图：数据流、状态机、错误路径]
          [测试矩阵、失败模式、安全问题]

你：      批准方案，退出 plan 模式。
          [写了 2,400 行，跨 11 个文件，约 8 分钟]

你：      /review
          [自动修了 2 个] [提问] 有个竞态条件 → 你批准，修

你：      /qa https://staging.myapp.com
          [真的打开浏览器，点着走完整条流程，找到一个 bug 并修掉]

你：      /ship
          测试：42 → 51（新增 9 个）。PR：github.com/you/app/pull/42
```

你说的是「每日简报 App」。它说「你在做一个幕僚长 AI」——因为它听的是你的**痛**，
不是你的功能需求。八条命令，从头到尾。

**这不是 copilot，这是一支队伍。**

每一步都不是「问模型一个问题」，是**按一份固定的工序走**。
工序在 `<skill>/SKILL.md` 里，你可以打开读，也可以改。

## 为什么要这么设计

因为模型不缺能力，缺的是**纪律**。

`/review` 之所以有用，不是因为它调了个更聪明的模型，
而是因为它在提示词里写死了「不许说『看起来不错』，要么指出具体行号，
要么明确说这一段你没验证」。

**这就是为什么这些技能全是 Markdown 文件**——你能看见纪律是什么，
也能针对自己的项目改它。

## 工序（The sprint）

gstack 不是一堆工具，是**一道工序**。技能按一次冲刺的顺序排：

**想 → 规划 → 写 → 评审 → 测 → 发 → 复盘**

每一个技能的产出，是下一个技能的输入。`/office-hours` 写出一份设计文档，
`/plan-ceo-review` 读它；`/plan-eng-review` 写出测试计划，`/qa` 接过去；
`/review` 抓到的 bug，`/ship` 负责验证修没修。

**没有东西会掉在地上，因为每一步都知道上一步干过什么。**

| 技能 | 你的专家 | 他干什么 |
|------|---------|---------|
| `/office-hours` | **YC Office Hours** | 从这里开始。六个逼问，在你的产品动手写代码之前就把它重新框一遍。它会顶你的框架、挑战你的前提、给你几条不同的实现路线。产出的设计文档喂给下游所有技能。 |
| `/plan-ceo-review` | **CEO / 创始人** | 重新想这个问题。找出你的需求里藏着的那个 10 分产品。四种模式：扩张、选择性扩张、守住范围、砍。 |
| `/plan-eng-review` | **工程经理** | 把架构、数据流、图、边界情况、测试全部锁死。把藏起来的假设逼到台面上。 |
| `/plan-design-review` | **资深设计师** | 给每个设计维度打 0-10 分，说清楚 10 分长什么样，然后动手改方案。专治 AI 味。 |
| `/plan-devex-review` | **开发者体验负责人** | 交互式的 DX 评审：探索开发者画像、对标竞品的上手时间、设计你的「魔法时刻」、一步步追摩擦点。 |
| `/review` | **Staff 工程师** | 找那种过了 CI、但一上生产就炸的 bug。明显的直接自动修。 |
| `/deslop-shared-libs` | **共享代码评审** | 在最近的工作里找值得抽出来的共用代码。最多比 5 个机会，推荐最好的 3 个。只给建议，不动手。 |
| `/test-audit` | **测试审计** | 扫一遍现有测试，找出「维护成本大于它保护的东西」的那些：源码 grep、重复、没有断言的探针、只为测试存在的导出。只报告，你批准了才批量处理。 |
| `/investigate` | **调试者** | 系统性的根因调试。铁律：没有调查就没有修复。追数据流、验假设、连续 3 次修不好就停。 |
| `/qa` | **QA 主管** | 真的开浏览器、真的点。复现 bug、写出会失败的回归测试、修掉根因、再验一遍才提交。 |
| `/cso` | **首席安全官** | 安全审计：先建应用模型，只报有支撑的发现，独立挑战每个结论，并显式说明覆盖范围。 |
| `/ship` | **发布工程师** | 同步主干、跑测试、审覆盖率与文档，然后验证、推送、开 PR。 |
| `/canary` | **SRE** | 上线后的监控回路。盯着控制台报错、性能回退、页面挂掉。 |

> 完整的分工表在 [`SKILLS.md`](SKILLS.md)。

### 该跑哪个 review？

| 你在给谁做 | 写代码前 | 上线后 |
|-----------|---------|--------|
| **终端用户**（UI、网页、App） | `/plan-design-review` | `/design-review` |
| **开发者**（API、CLI、SDK、文档） | `/plan-devex-review` | `/devex-review` |
| **架构**（数据流、性能、测试） | `/plan-eng-review` | `/review` |
| **全都要** | `/autoplan` | — |

`/autoplan` 会自动跑 CEO → 设计 → DX → 工程，并且**工程永远排在最后**。
这个顺序是刻意的：工程评审审的是**被前面几轮改完之后的最终方案**，
而不是一份已经被推翻的初稿。

## 平行的冲刺

一个冲刺就好用。**十个同时在跑，才是质变。**

原作者的说法是他常态跑 10-15 个并行冲刺。靠的不是模型更强，是**工序**——
十个 agent 没有工序就是十份混乱，有工序的话每个都知道自己该干什么、
什么时候该停。你管它们的方式，跟 CEO 管团队一样：
**只盯真正重要的决策，剩下的让它自己跑。**

原作者说 `/qa` 是让他从 6 个并行涨到 12 个的那个解锁点——
因为 **agent 终于有眼睛了**。

**智能 review 路由**是同一个道理。就像一家公司：CEO 不用去看一个基础设施的
bug 修复，后端改动也不需要设计评审。gstack 会记你跑过哪些评审，
判断这次该跑哪个，然后直接做。

> **这个版本要在 DeepSeek 上做到这一点，瓶颈是配额，不是模型能力。**
> 工序本身和上游完全一样——换的只是后端，以及账单上的那个名字。

## 卸载 / 回滚

因为这个版本是**一个补丁**，回滚特别干净——没有「卸载程序」要跑：

```bash
cd /path/to/gstack        # 你的 gstack 检出目录

# 补丁还没提交
git checkout .

# 补丁已经提交了
git apply -R patch/gstack-deepseek-port.patch

# 或者直接退回纯上游
git reset --hard origin/main
```

`git reset --hard origin/main` 之后你就回到了**未经改动的上游 gstack**。

这也是为什么不建议手改 `SKILL.md`：那些文件是**生成的**，
`bun run build` 会把它们全部重写一遍，你的手改会无声消失。

## 关于遥测

上游 gstack 的遥测**默认关闭**，而且只上报技能名、耗时、版本、操作系统、
错误类别这类元数据。它明确声明**绝不上报**：代码、文件路径、仓库名、
分支名、提示词，或任何你写的内容。要发也发到 Supabase（开源的 Firebase 替代品），
表结构在仓库里，可以自己核对。

**这个版本一行遥测代码都没有动。** 换句话说：

- 上游发什么，这里发什么；上游不发什么，这里也不发
- 唯一的区别是**模型调用打到了 `api.deepseek.com`**，而不是 Anthropic
- 想彻底关掉：`gstack-config set telemetry off`

> 我们改了 6 个文件，全部是**模型调用怎么走**这件事。遥测不在其中。
