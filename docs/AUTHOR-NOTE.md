## See it work（它怎么干活）

一次典型的冲刺长这样：

```
你：/office-hours        → 把你的模糊想法逼成一个能说清楚的方案
你：/plan-ceo-review     → CEO 视角挑刺：这东西到底该不该做
你：/plan-eng-review     → 工程视角挑刺：这么写会不会塌
你：/plan-design-review  → 设计视角挑刺：用户会不会一脸问号
你：（写代码）
你：/review              → 上线前找生产环境级别的 bug
你：/qa                  → 真的开浏览器点一遍
你：/ship                → 合并基线、跑测试、改版本号、写 CHANGELOG、开 PR
你：/canary              → 上线后盯着
```

每一步都不是「问模型一个问题」，是**按一份固定的工序走**。
工序在 `<skill>/SKILL.md` 里，你可以打开读，也可以改。

## 为什么要这么设计

因为模型不缺能力，缺的是**纪律**。

`/review` 之所以有用，不是因为它调了个更聪明的模型，
而是因为它在提示词里写死了「不许说『看起来不错』，要么指出具体行号，
要么明确说这一段你没验证」。

**这就是为什么这些技能全是 Markdown 文件**——你能看见纪律是什么，
也能针对自己的项目改它。
